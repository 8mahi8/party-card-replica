## 状態モデル

```js
{
  schemaVersion: 2, rulesetId: "wiki-2025-lab",
  revision: 0, phase: "turn",
  activePlayerId: "A",
  players: [
    {id:"A",hp:40,mp:10,money:20,
     hand:[{instanceId:"ci-1",definitionId:"w016"}],learned:[]},
    {id:"B",hp:40,mp:10,money:20,
     hand:[{instanceId:"ci-2",definitionId:"d001"}],learned:[]}
  ],
  nextInstanceSerial: 3, rngSeed: 1,
  pending: null, processedCommands: []
}
```

`createStagingRoom()` の初期手札指定は**開発専用**。本番は監査済みカードデッキから、権威側が配布する予定。クライアントがカードを自由に選べる形式では公開しない。

## コマンドと遷移

- `playCards`：手番プレイヤーが順序付きcardInstanceIdを宣言。ターゲットが他人なら `turn → defense`。自分自身なら `turn → resolving`（自爆は防御不可）。
- `defend`：防御者が自分のカードIDを選択するか、空配列で無防御を指定。`defense → resolving`。
- `resolving`：意図を保存したまま**G3待機**。この段階ではHP・MP・手札を消費しない。攻撃・勝敗が決定したとは主張しない。
- 状態 `revision` は、受理した操作ごとに1増加。古いrevisionの別コマンドは拒否。
- 同じ `commandId` と同じ内容の再送は冪等な無操作。同じIDで内容を変えると拒否。認証された席との一致は再送判定より先に検査する。
- `authorizedSeatId` は**信頼できる通信層から渡す想定**。ユーザーのブラウザが送ったactorIdだけでは認証済みにならない。

G2が検査するのはプレイヤー・ターン・カードの所持・基本分類と選択順の構造。特殊効果の組み合わせとMPの厳密な合法性は**G3の共通コンパイラ**に任せる。現状の制約が原作の合法手を誤って排除しないよう、自分への攻撃と攻撃奇跡を受理できる。

## 秘匿

`viewStagingRoom(state, viewerId)` は**自分自身の手札IDだけ**を返し、相手のカード種類・instanceId・内部乱数seed・processedCommands・未解決のカード選択内容を伏せる。相手には手札枚数のみ。これを送信することで表示上の漏洩を防ぐ設計。

注意：この投影だけではセキュリティは完成していない。どの人にどのviewを送るかの**本人認証・アクセス制御は通信層で必要**。また、公開コードに管理者鍵を埋め込まない。

## 未実装とG3のゲート

- ダメージ・装備防御・反射・奇跡・精霊・補充・勝敗はG3で処理。
- `resolving` から次のターンを進める処理はまだない。
- 一致する過去のcommandIdは部屋が存在する間記録する。恒久的なリプレイ履歴ではない。長時間試合のメモリと部屋終了時の破棄を後で計測する。
- revisionの一致検査だけでは**別クライアントによる同時更新の原子性は確保されない**。実際のストレージのCAS/トランザクションが必要。
- 再接続、通信遅延、ゲスト固まり、旧Safariの動作と長時間プレイは**未検証**。
- 既存デモやmainにG2を統合するのはG3の回帰テストを通してから。
