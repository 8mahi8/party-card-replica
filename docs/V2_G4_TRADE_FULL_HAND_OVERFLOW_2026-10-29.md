# G4 原作再現｜手札18枚の相手への「売る」／19枚目の押し出し

2026-10-29、`8mahi8/party-card-replica`、開発ブランチ `refactor/v2-foundation-review-20261027`、Draft PR #1。

## 今回確認できたルール

- [アニヲタWiki／ゴッドフィールド](https://w.atwiki.jp/aniwotawiki/pages/47010.html)：「手札18枚の相手へ19枚目を押し付けると、**既存の18枚の神器から1枚が消える**」と明記。
- [2025年の1000試合プレイヤー解説](https://note.com/md_stardustman/n/nfc5dfb559f95)：手札上限は**18枚**。売る・買うで超えると**ランダムに押し出されてなくなる**。ただし「設置された奇跡も含む」という説明あり。
- [2026-09-30の現行プレイヤーQ&A](https://detail.chiebukuro.yahoo.co.jp/qa/question_detail/q14331754699)：「祈る」で18枚の状態から追加ドローすると、ランダムで1枚が捨てられるとの報告。[wiki仕様](https://w.atwiki.jp/piong/pages/16.html)にも同様の記述。祈ると取引は異なるが、同じ上限の根拠として参照。
- 本家現行クライアントの**実DOM/API/動画を直接取得してはいない**。ランダムというルールは裏付けられるが、内部PRNGの方式・抽選分布までは直接確認できない。今回の研究版は既存シリアライズ可能な`drawRandom32`を使用する**決定論的fixture**。原作がxorshift32であるとは主張しない。

## 変更した設計

従来、買い手の物理手札が18枚のときは`Buyer hand cap needs original-game verification`で無条件拒否していた。今回から次のルールに変更。

1. **受け取る前の手札が17枚以下**：商品をそのまま受け取る。乱数は消費しない。
2. **既存の物理手札が18枚**：元の18枚の個体IDから乱数で**ちょうど1枚**を選び、既存の1枚を取り除いてから**売られた商品を必ず受け取る**。物理手札は18枚のまま。選ばれる対象に新商品の個体IDは含めない。
3. **売り手の「売る」カードと商品の消費**：既存どおり、取引カードは通常の補充対象、商品そのものは補充なし。取引対象の個体IDを相手の手札に移す（コピー・再生成はしない）。
4. **買い手の代金支払い**：既存の`planForcedSalePayment`で所持金→MP→HP、買い手が死亡するケースは**まだ拒否**。今回の資料で致死的な「売る」は可能と確認できたが、死亡時に支払い不足の金額がどう入金されるか・原子処理と終了の優先順位の直接証拠がないので、無理に一括実装していない。
5. **スーパーミラーで取引を返した場合**：商品は元売り手に残り、買い手の手札には何も追加されない。そのため、18枚でも**押し出しの乱数を消費しない**。
6. **習得済み奇跡が手札上限に絡む場合**：2025年資料に「設置された奇跡も含む」という記述があり、物理手札と習得済み奇跡のどちらを押し出すか未確認。`buyer.learned.length>0`かつ`hand.length + learned.length >= 18`の場合は、今後の直接照合まで**明示的に拒否**し、間違った削除を防ぐ。

## コード構造

- **新規 `v2/hand-overflow.mjs`**：純粋関数`planIncomingHandTransfer(hand,seed)`。
  - 物理手札の個体ID重複と最大枚数、シードを検証。
  - 17枚以下：`{willOverflow:false,evictedInstanceId:null,evictedIndex:null,nextSeed:seed}`。
  - 18枚：旧手札18枚中の抽選位置／個体IDと`nextSeed`を凍結した計画として返す。元の配列・オブジェクトは変更しない。
  - 「売る」「買う」など今後の**手札移動を伴う効果の共通部品**として使える。
- `v2/trade-sale.mjs`：満杯の物理手札を許可。プレビュー結果`willOverflow`を追加。習得済み奇跡を含む曖昧な上限ケースだけ保留。
- `v2/effect-runner.mjs`：受け入れられた売却の`uncontestedSale`効果から上記共通計画を使用。既存の18枚のカードを1枚消去し、乱数シードを1回だけ進め、売却商品を`instanceId`を変えずに追加。`handOverflow`イベントは`playerId`・失った個体ID・定義ID・原因`trade`を記録。**ゲーム本体では元stateを直接変更せず、cloneしたroomで決済**。
- `v2/demo/build.mjs`と`v2/demo/standalone.html`：共通モジュールをeffect-runnerより先に取り込み、オフラインiPad試遊HTMLをコードと同期。
- `main`と学校Google Sites公開版は変更しない。

## テスト

既存の`tests/uncontested-sale-v2.test.mjs`の「手札上限なら拒否する」テストを、原作資料に沿う**元18枚のうち1枚だけ失う**テストへ更新。

新規`tests/trade-hand-overflow-v2.test.mjs`は**11件**：

- 17枚以下なら乱数なし、18枚なら**1回**消費。凍結されたプラン／元state不変。
- 20,000の異なるシードで18箇所が抽選先として到達可能（**原作確率分布の証明ではない**）。
- 重複した物理個体ID、不正シード、19枚の不正入力の拒否。
- 18枚買い手への金のこん棒25円売却で、旧1枚のみ喪失・**売られた金のこん棒は必ず保持**・商品個体ID維持・¥とMP適切決済・新ID重複なし・再現可能シード。
- 17枚で19枚目にならない購入では抽選なし。
- 3人対戦で第三者の手札・ステータス不変。
- 認証済みの`declareSale`→`respondSale`（受け入れ）で18枚上限処理を共通エンジンにより実行。
- 買い手18枚でもスーパーミラーで返せば旧カードは消えず乱数も消費しない。
- 習得済み奇跡を含む上限曖昧ケースは**fail-closed**、元状態不変。上限未満なら利用可能。
- 致死的取引は従来どおり保留。前のテストで例外を隠すことはない。

実装変更後の最新コミットに対し Node／Chromium／WebKit の各GitHub Actionsを実行し、最終結果をDraft PR #1へ記録する。
