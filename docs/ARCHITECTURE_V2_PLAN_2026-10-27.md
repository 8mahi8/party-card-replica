# V2開発基盤レビュー・移行計画（2026-10-27）

対象：学校iPad Safariで友人が遊ぶカード対戦ゲーム。**原作の判定を可能な限り忠実に再現する**。本書は設計案であり、現行mainや学校Google Sites版は変更しない。

## 決定した前提

1. 基本は1vs1、将来的な最大9人・全体攻撃を妨げない。
2. Google Sitesの「HTML/CSS/JavaScriptの埋め込みコード」を使い続ける。GitHub PagesのURLを埋め込む方式に切り替えない。
3. 開発用モジュールは分割、本番配布物だけ単体HTMLへビルド。無料運用・旧iPadの性能と互換性を優先。
4. カードの大半はデータ定義で登録。ただし複雑な固有カードを表現するための共通効果ハンドラも必要。万能DSLを先に作り込みすぎない。
5. 登録済み68種類のデータと既存自動テストは捨てない。新エンジンへの移行は段階的に実施する。
6. 原作資料に版差があるため、353種類／500枠は「2025年Wikiの参照値」。現行版で必ず正しいと断定しない。
7. ユーザーが不要としている恒久的対戦ログ・リプレイは導入しない。開発中だけ一時トレースを利用可能とする。

## V2の4層構造

(1) cards / catalog：
カード種類の定義：種類ID、分類、使用モード、基本攻守値、価格、属性、抽選重み、効果タグ、出典・対象バージョン。手札内の個々のカードには新しいinstanceIdを割り当てる。

(2) core：
サーバー／BOT／ローカル／テストが同じ受け口を使う。操作を受理し、プレイヤー・ターン・選択順を検証 → 費用を確定 → 効果キューを積む → 防御・反射など追加の判断があれば停止 → 解決 → 手札補充 → 次手番へ。イベント、待機中の効果、状態はJSONに保存できる単純なデータ。無効な操作で状態を変えない。

(3) views + UI：
自分の手札は表示、相手の手札は枚数だけ表示。UIは入力を送るだけで勝敗・合法性を独自判断しない。デスクトップ/旧Safariを同じ描画経路で扱う。

(4) transport + build：
接続・順序・再接続の担当を戦闘ルールから完全分離。ルームrevisionとcommandIdによる重複対策。最終的なGoogle Sites版は単体HTML、サービスの秘密鍵や管理者権限を埋め込まない。

## カードテンプレート（例：参照用の架空データ）

    {
      id: "weapon.basic.10",
      family: "weapon",
      stats: { attack: 10, guard: 0, mpCost: 0, price: 4 },
      element: "none",
      playModes: ["mainAttack"],
      drawWeight: 7,
      effects: [],
      source: { ruleset: "community-2025", confidence: "secondary" }
    }

反射カードの追加効果は以下のように登録する：

    effects: [
      { when:"defense.redirect", type:"redirectAttack",
        params:{mode:"reflect", scope:"neutralWeapon"} }
    ]

effects.typeは**既知のホワイトリスト**だけ。任意のJavaScriptコードをカードデータから実行しない。基本値だけのカードには追加ハンドラが要らないが、特別な例外は専用の小さなハンドラで実装。

## コマンド契約（例）

    {
      commandId: "per-submission-id",
      roomRevision: 12,
      actorId: "seat-1",
      type: "playCards",
      orderedInstanceIds: ["ci-017", "ci-029", "ci-081"],
      targetIds: ["seat-2"]
    }

順序が重要。例えば「武器 → 火の玉 → 火の玉 → 精霊」を一つの注文として検証する。カード配列の場所ではなく、個々のカードのIDで指定する。元のstateを破壊せず、新しいstateと表示イベントを返す。ダメージ直前の反射／防御はpendingResolutionを保持し、その場で相手のコマンドを待つ。必要なときだけ状態遷移を進める。

## オンライン対戦に入る前のゲート

- 真の状態（カード山と両プレイヤーの手札）を全クライアントに渡さない。プレイヤーごとのviewを用意する。
- 一般にホスト権威方式はホスト切断時に試合が止まる。無料バックエンドに権威を置けるか、学校iPadで匿名ログインが制限されないか、実機比較して決める。
- 候補は Firebase Realtime Database / Supabase Realtime / 無料WebSocket系。ただし費用・利用制限・学校Safari対応を現行公式情報と実機で確認して採用する。
- 二重送信、再接続、同時操作、ターンの取り違え、ゲスト画面停止を検証する。URLを知るだけで全員の非公開手札を読めないようにする。
- 対戦の恒久的履歴は不要。シリアライズ可能な短期状態は再接続のため保持してよい。

## 進め方（順序と完了条件）

G0 現状を固定：既存mainと現在の検証用ホットシートは保持。新基盤はrefactorブランチ内で研究。失敗した移行をいつでも破棄可能。

G1 データとカード実体：スキーマ・instanceId・版付きカタログを実装。カード68種類を自動変換して元の数値一致を監査。重複した同種カードを区別できること。

G2 コマンドと状態：revision、ターン・対象・選択順検証、プレイヤー別ビュー、固定seedの乱数。誤操作・重複・古いrevision・相手手札露出のテスト。

G3 効果エンジン：宣言、支払い、属性、攻撃・防御、止める、反射、習得、補充のキューを構築。現在の通常攻撃・防御・反射・奇跡・精霊の主要回帰ケースと結果を比較。**このゲートまでは新カードの大量追加をしない**。

G4 原作照合：原作の動画/実機によるケースをgolden testに追加し、確かな出典のカードからデータ移植。未確認の効果は推測で実装しない。

G5 試遊画面：新coreを使うUI、旧iPad横向き、単体HTML化、手札操作と防御のブラウザ操作テスト。

G6 1vs1通信：実際の学校の端末でルーム接続、手札の秘匿、送信重複、ゲスト表示、切断復帰、連続試合を検証。無料運用の前提を守る。

G7 残りの特殊カード・原作ケースを網羅する。「353種類登録済み」でも「完全再現完了」とは呼ばない。

## 採用前の条件

- 現行main・Google Sites版を上書きしない。
- 既存テストを減らさず、V2で少なくとも10件の元ルール回帰テストを再現。
- カード追加がデータ登録だけで済む基本ケースと、特殊ハンドラが必要なケースを1つずつ証明する。
- 実機・通信のゲートなしに「遊べるオンライン版」と発表しない。

## 結論

**大規模な全面書き直しを今日始めるのではなく、データ/コマンド/効果/表示の4層を先に小さく証明してから移す。** 今の資産は活かす。設計の中心は「カード定義とプレイ中のカード実体の分離」「選択順が保存された共通アクション」「順序付き効果処理」「オンライン時の状態revisionと秘匿手札」。この設計でカードが増えても仕様とテストを独立に保守できる。
