# G3/G7｜特殊武器に進むための命中境界レビュー（2026-10-30）

## 今回の到達点

**「攻撃後効果の実カード実装」はまだしていない。** 既存エンジンの命中・補充・復活の実コードを監査し、特殊カードを誤って数値武器として登録しないための最小の純粋な契約を開発ブランチに追加した。学校のGoogle Sitesとmainには変更を加えない。

- 新規 `v2/hit-outcome-boundary.mjs`：通常の命中、0ダメージ、オーバーキル、闇の即死、HP0後の受動復活を、**観測値だけ**を使って区別する。`damage`（印字/計算上のダメージ）と`hpLost`（実際のHP減少）を混同しない。`overkill`は通常のHP算術時だけ数値で表し、即死は`null`（算術上の過剰ダメージと同一視しない）。
- 新規 `tests/hit-outcome-boundary-v2.test.mjs`：12個のNodeテスト。正規値、完全防御、HPぴったり、オーバーキル、即死、HP10復活、異常値と矛盾したHPを拒否する回帰。
- **既存`v2/effect-runner.mjs`、デモHTML、カード数、ドロー仕様には手を加えていない。** この純関数は次回の共通イベント接続前の境界契約であり、現在の戦闘へ未配線。

## 2026年時点の公開情報と残る解釈

1. [Piong神器一覧（2026-03-18更新）](https://w.atwiki.jp/piong/pages/15.html)／[まかろんの神器一覧（2026-02-28）](https://macarongamemo.com/entry/godfield-artifact)：**ゴーストソード（攻7、¥10、0.2%）**はHP吸収とされ、まかろん資料では「与えたダメージ分」と説明される。**「攻7を越えるオーバーキル時に何HP吸うか」「闇即死を付加したとき」「被害者が太陽のお守りで復活したとき」「反射して別人へ当たったときの吸収者」**の組み合わせは未確認。二次資料だけで金額・HPを確定しない。
2. 同資料および[実プレイヤーの解説（2023年）](https://idea427.hatenablog.com/entry/2023/07/31/192159)：**のこぶんぶん（攻3、2回攻撃）**は追加武器の攻撃値が2回に作用するとの記録。ただし実処理上の「各回の防御・反射・HP0復活・カード消費と補充のタイミング」を原作映像で未確認。単純に「ダメージを2倍する」実装は禁止。
3. [Piong神器一覧](https://w.atwiki.jp/piong/pages/15.html)と[災い一覧](https://w.atwiki.jp/piong/pages/23.html)：**地獄のハサミ（攻8）**は対象に1以上のダメージを与えた場合に地獄病。**疾風剣（攻9）**は同条件で風邪。災いはターン終了時効果や悪化判定があり、単なる画面表示のバッジで完成と扱わない。
4. これらは原作の現行クライアントをAIが直接操作した確認ではない。異なる年の資料は版差がある可能性を残す。

## 実コードを確認した処理境界

| 処理 | 現在の実装 | 特殊効果で気を付ける点 |
|---|---|---|
| 操作受付 | `v2/staging-room.mjs`／`room-transition.mjs` | actor/seat認証、commandId、expectedRevision、選択順を先に検査 |
| 攻撃コンパイル | `v2/ordered-attack.mjs` | 武器・追加武器・奇跡の合法な組合せだけ確定。特殊武器を単に通常武器として処理しない |
| 反射・弾く | `v2/redirect-resolution.mjs`／`redirect-route.mjs` | 初回ホップに攻撃の消費を済ませ、同じ`attackContext`を次ホップへ保持。効果は最終的な被弾対象だけで解決する必要あり |
| ダメージ・HP0 | `v2/basic-resolution.mjs`→`effect-runner.mjs` | `hit`の後、受動`onZeroHp`でHP10復活を判定。イベントの`hpAfter`は復活前。次段の特殊効果との優先順は未確認 |
| 受動補充 | `v2/effect-runner.mjs` | spendは補充枠へ1回だけ積み、`refill`で一度だけ補充。死者は補充されない |
| 秘匿表示 | `v2/staging-room.mjs`／`dream-appearance.mjs` | 真の神器IDや夢の実体を公開イベントに載せない |
| 単体デモ | `v2/demo/build.mjs` | 今回は未接続なので29モジュールの再生成不要。新モジュール配線時は依存順と出力完全一致を検証 |

## 次に実装する順序

1. **HP吸収の効果タグ**：`afterHit`と厳密に型検証するパラメータを`foundation`へ登録する前に、上記の特殊ケースで何を吸収量とするかの優先順位を文献・原作実例で照合。まず普通の無属性・無反射・非致死・防御あり／なしのケースで小さく接続。
2. **イベント単位の一度きり清算**：支払った攻撃カードの物理instanceIdと、最終の被弾対象、before/afterHP、最終ホップ、未実行効果のIDを保存し、反射・再送時に同じ効果を二度かけない。全てサーバー権威側（現在はfixture）で解決。外部から任意の`heal`や`status`命令を受け付けない。
3. **2回攻撃**：2つの被弾イベントと防御介入の構造を作ってから登録。2×ダメージ1発というショートカットは不可。
4. **災い**：付与条件だけでなく状態機械・治癒・ターン末・悪化・死亡復活を個別資料で確認してから実カードを収録。
5. 既存のオーラ／火の玉／精霊／スーパーミラー／夢表示／太陽のお守り／固定補充と、WebKitのタップ試験を全回帰。部分116種／305参考枠を正規山札には流用しない。
